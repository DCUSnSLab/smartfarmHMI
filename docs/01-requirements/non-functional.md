# 01-2 · 비기능 요구사항

## 1. 확장성

- 데이터 타입·크기·주기가 확정되지 않았으므로, 특정 스키마에 고정하지 않고 필드 확장이 쉬운 구조로 설계한다.
- 장비(로봇·생육기·탱크·워크스테이션·센서) 추가는 등록만으로 가능해야 한다 (코드 변경 불필요).
- **장치가 자신의 데이터 항목을 스스로 선언한다.** 장치는 접속 시 birth 메시지로 발행할 항목·타입·초기값을 알리고, 미들웨어 서버는 이를 근거로 수집 대상을 구성한다. 외부 설정 파일에 항목 목록을 하드코딩하지 않는다 (`../03-architecture/communication-interface.md`). 데이터 항목이 늘어도 서버 코드를 고치지 않아도 되게 하는 것이 목적이다.
- **다농장**: 설계·구현은 농장 N개를 전제로 하고, 2차년도 실운영은 농장 1개다. 모든 엔터티는 농장 식별자를 갖고 MQTT 토픽도 농장 단위로 계층화하므로, 농장 추가 시 스키마·토픽 구조를 바꾸지 않는다 (OPN-23).
- LED 조명은 2차년도에 그룹/전체 단위로 제어하되, 이후 파레트별 개별 제어로 확장 가능한 구조로 설계한다 (FR-10·11, OPN-14).

## 2. 안전

### 2.1 두 가지 정지 기능의 구분

정지 기능은 표준상 요구사항이 전혀 다른 두 가지로 나뉜다. 문서·UI·코드 전반에서 혼용하지 않는다.

| | 물리 비상정지 | 원격 전체 정지 |
|---|---|---|
| 표준 | ISO 13850 (비상정지 기능 설계 원칙) | IEC 60204-1 정지 기능 |
| 정지 범주 | **Stop Category 0 또는 1** | **Stop Category 2** (제어된 정지, 액추에이터 전원 유지) |
| 안전등급 | 안전 기능 | **비안전등급 — 운전 정지** |
| 장치 형태 | 물리적 직접개로(direct-opening) + 기계식 래치 | 웹앱 화면상의 조작 |
| 해제 | **현장에서 의도적 수동 조작으로만.** 리셋 후에만 재기동 가능 | 웹앱에서 해제 가능 (권한 수준 OPN-18) |
| 담당 | 엣지·하드웨어팀 (**개발 범위 밖**) | 우리 팀 (범위 내) |
| 관련 요구사항 | FR-36 (상태 표시 전용) | FR-35 |

### 2.2 근거

- **ISO 13850은 터치스크린·화면상의 그래픽 아이콘을 비상정지 장치로 인정하지 않는다.** 플러시·멤브레인 스위치나 화면 버튼도 허용되지 않으며, 접점 분리가 스프링이나 소프트웨어 로직이 아니라 직접적인 기계적 연결로 이뤄져야 한다. 래치 없는 개로, 개로 없는 래치가 모두 금지된다. 원격·무선 비상정지는 허용되지만 매우 엄격한 규정을 따른다.
- **IEC 60204-1·ISO 13850·NFPA 79는 비상정지를 Stop Category 0/1로 제한한다.** Category 2는 비상정지에 적합하지 않으며 **운전·정상 정지 기능 전용**이다.
- 비상정지는 **다른 모든 동작·기능보다 우선(override)** 하고, 리셋(unlatch)될 때까지 정지 상태를 유지하며, 리셋 후에만 재기동이 가능하다.
- **MQTT는 안전등급 통신이 아니다.** 따라서 안전 기능을 MQTT 경로에 의존시킬 수 없다. 웹앱→엣지 경로로 내려가는 정지 명령은 그 성격상 운전 정지(Category 2)일 수밖에 없다.

이 근거에 따라 **웹앱이 제공하는 정지 기능은 "비상정지"가 아니라 "원격 전체 정지"** 이며, 실제 비상정지는 현장의 물리 장치가 담당하고 웹앱은 그 상태를 표시만 한다.

### 2.3 원격 전체 정지 요구사항 (FR-35)

- 발동 전 확인 절차를 둔다 (오조작 방지).
- 발동 중 **자동 스케줄 발행과 원격 제어 명령을 차단**한다. 차단은 미들웨어 서버에서 수행하며, 웹앱 UI 비활성화에만 의존하지 않는다.
- 발동 중임을 모든 화면에서 지속적으로 표시한다.
- 발동·해제 이력(발동자·시각·대상 범위·사유)을 보존한다.

### 2.4 물리 비상정지 상태 표시 요구사항 (FR-36)

- **웹앱에 해제 경로를 두지 않는다.** 화면에는 현장에서 직접 해제해야 함을 안내한다.
- 원격 전체 정지와 시각적으로 구분한다. 두 상태가 동시에 성립할 수 있으므로 각각 독립적으로 표시한다.
- 상태를 취득할 수 없는 경우(OPN-19 미해결) 이 기능은 3차년도로 이월하고, 웹앱에 "상태 미확인"으로 표시하지 않는다 — 잘못된 안심을 유발하지 않기 위해 표시 자체를 노출하지 않는다.

### 2.5 작업자 안전

- 로봇 등 장비의 작업자 안전·충돌 방지는 엣지·하드웨어 계층의 책임이다. HMI는 정지 상태와 이상 상태를 표시하고 알림을 전달하는 역할을 한다.

## 3. 페일세이프

통신 단절 시 동작을 3계층으로 정의한다. 상위 계층이 실패해도 하위 계층이 독립적으로 안전 상태를 유지해야 한다.

| 계층 | 담당 | 동작 |
|---|---|---|
| ① 엣지 | 엣지 (범위 밖, **인터페이스 계약으로 명시**) | 미들웨어 서버와 통신이 끊기면 진행 중인 파레트 임무를 안전한 위치에서 정지하거나 원래 슬롯에 반납하고, 신규 임무 수락을 중단한다 |
| ② 미들웨어 서버 | 우리 팀 | 엣지의 LWT/death 메시지 또는 keep-alive 만료를 감지하면 해당 농장의 **자동 스케줄 발행을 보류**하고 알림을 발생시킨다 (FR-32·37) |
| ③ 웹앱 | 우리 팀 | 통신 단절 상태를 표시하고, 해당 범위의 제어 UI를 비활성화한다. 마지막 수신 시각을 함께 보여 데이터가 최신이 아님을 알린다 |

- 엣지의 동작(①)은 개발 범위 밖이지만, 미들웨어 서버가 노출하는 엣지 통신 인터페이스의 계약 사항으로 문서화해 엣지팀에 전달해야 한다.
- 미들웨어 서버가 재시작되더라도 마지막으로 알려진 장치 상태를 복구할 수 있어야 한다. MQTT retained 메시지가 이 역할을 한다 (§4).

## 4. 통신 신뢰성

`../03-architecture/communication-interface.md`의 규격과 짝을 이루는 품질 요구사항이다.

- **QoS 1을 기본으로 한다.** 스마트팜 환경에서 QoS 1이 가장 안정적인 특성(지연 약 150ms, 수집률 99% 이상, 손실률 0.5% 이하)을 보이는 것으로 보고된다. QoS 0은 손실이 허용되는 항목에만, QoS 2는 사용하지 않는다(오버헤드).
- **명령은 멱등(idempotent)해야 한다.** QoS 1은 중복 배달이 가능하므로, 모든 제어 명령에 명령 식별자를 두고 수신 측이 중복을 제거한다. 같은 명령이 두 번 도착해도 두 번 실행되지 않아야 한다.
- **명령 토픽에 retained 메시지를 쓰지 않는다.** 명령을 retain하면 장치가 재접속할 때마다 과거 명령이 다시 배달되어 의도치 않게 재실행된다. retained는 상태·최신값·birth 계열에만 사용한다.
- **모든 제어 명령은 응답(ACK)과 타임아웃을 갖는다.** 타임아웃 내 응답이 없으면 실패로 처리하고 사용자에게 알린다. 명령을 보낸 것과 실행된 것을 구분해 표시한다.
- **최신값은 retained 메시지로 보관한다.** 신규 구독자(대시보드 최초 진입, 서버 재시작)가 다음 주기를 기다리지 않고 즉시 최신값을 받을 수 있어야 한다.
- **오프라인 감지는 LWT에 의존한다.** 장치는 접속 시 LWT를 등록하고, 브로커가 keep-alive 만료를 감지하면 death 메시지를 대신 발행한다. 애플리케이션이 별도로 폴링해 생존을 확인하지 않는다.

## 5. 접근성

고령 사용자의 현장 사용을 전제로 한다. 실내외 조명 조건 차이와 장갑 착용 상태의 조작을 고려한다.

- **글자 크기 3단계**(표준 / 크게 / 아주 크게)를 제공하고, 글자와 터치 영역이 함께 확대되어야 한다. 선택한 단계는 다음 접속에도 유지된다.
- **본문 13px 이상, 강조 수치 22px 이상, 터치 영역 40px 이상**을 지킨다.
- **야외 고대비 모드**를 제공한다. 직사광 아래 가시성을 확보하기 위한 명암·채도 강화 표시다.
- 상태를 색으로만 구분하지 않는다. 색과 함께 문자·도형(아이콘·점 표시 등)을 병기해 색 구분이 어려운 사용자도 판별할 수 있어야 한다.
- 글자 크기 확대가 화면 구조를 깨뜨리지 않아야 한다. 상단 고정 네비게이션·고정 배치 요소와 충돌하지 않는 방식으로 구현한다 (구현 방식 참고: `../design/design-change-spec.md`).
