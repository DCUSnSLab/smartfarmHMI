## 0. 원칙

**한 필드는 한 축만 담는다.** 값 하나가 두 의미를 겸하면 하나가 다른 하나를 지운다.

0.2 에는 위반이 두 곳 있었다.

```
mission_state = idle|moving|working|charging|error
                └─ 어디까지 갔나 ─┘   └ 뭐가 틀어졌나 ┘   → 사건이 상태를 덮는다

engaged = true | false
                 └ "확인해 보니 풀림" + "확인하지 못함"    → 무지가 안전으로 읽힌다
```

두 곳을 갈랐다. 스키마 버전을 두 번 올리지 않으려고 한 번에 처리한다.

## 1. §4.2 robot_status — `phase` + `error`

```json
{
  "type": "robot_status",
  "version": "0.3",
  "farm_id": "seongju",
  "device_id": "robot-01",
  "position": { "x": 1.2, "y": 3.4, "frame": "farm_local" },
  "speed": 0.5,
  "battery_pct": 82,
  "charging": false,
  "phase": "working",
  "current_task_id": "pt-20260721-004",
  "error": null,
  "timestamp": "2026-07-21T10:00:00+09:00"
}
```

| 필드 | 값 | 성격 |
|---|---|---|
| `phase` | `idle` \| `moving` \| `working` \| `charging` | **상태** — 항상 값이 있고 관측으로 안다 |
| `error` | `null` 또는 객체 | **사건** — 발생해야 생기고 기록해야 남는다 |

`phase` 에 `error` 는 없다. 두 필드는 동시에 성립한다 — `phase: "moving"` + `error: {...}` 는
"이동 중 실패"다. 0.2 는 이 조합을 표현하지 못해 어느 구간에서 멈췄는지가 사라졌다.
임무 재개(증분 8)가 그 정보를 요구한다.

`error` 객체:

```json
"error": {
  "code": "nav_timeout",
  "message": "경로 탐색 시간 초과",
  "severity": "warning",
  "since": "2026-07-21T09:58:12+09:00"
}
```

- `code` 만 필수다.
- `severity` 는 `warning` \| `caution`. 생략하면 미들웨어가 `warning` 으로 본다.
- 미들웨어는 `error` 가 `null` → 객체로 바뀌는 **전이**에 알림을 만든다 (FR-32 `device_fault`).
  `dedup_key = robot_error:{device_id}:{code}` — 같은 오류가 이어지는 동안 재생성하지 않는다.

## 2. §4.7 estop_state — 3값

```json
{
  "type": "estop_state",
  "version": "0.3",
  "farm_id": "seongju",
  "device_id": "edge-01",
  "estop": "engaged",
  "source": "field_device",
  "timestamp": "2026-07-21T10:00:00+09:00"
}
```

| 값 | 뜻 | 엣지가 쓰는 때 |
|---|---|---|
| `engaged` | 눌려 있다 | 장치를 읽었다 |
| `released` | 풀려 있다 | **장치를 읽었다** |
| `unknown` | 모른다 | 아직 못 읽었거나 읽기에 실패했다 |

규칙은 다음과 같다.

- **`released` 는 장치를 실제로 읽어 확인했을 때만 보낸다.** 못 읽었으면 `unknown` 이다.
- **`unknown` 은 발행 측·수신 측 모두 `engaged` 와 동일하게 취급한다.** 엣지는 자체 정지
  로직에서 눌린 것으로 보고, 미들웨어는 정지로 판정한다.
- **`unknown` 일 때 `reason` 을 함께 보낸다** — `not_read_yet` \| `read_failed` \| `no_source`.
- **`unknown` 인 동안에도 발행한다.** 침묵하면 서버가 "모름"을 알 수 없다.
- **`estop` 필드가 없는 메시지는 `unknown` 으로 처리한다.** 하위호환 매핑(`engaged: false`
  → `released`)을 두지 않는다 — 그 매핑이 곧 되살리려는 결함이다. 이 경우 `reason` 은
  `no_report` 다.

0.2 의 결함은 다음 경로로 재현된다.

```
엣지 재시작 → estop{false} 초기화 → 서버에 "해제" 보고
현장 래치는 눌린 채 → 화면에서 정지가 풀린다
```

`engaged`·`unknown` 을 구분하되 판정은 같게 두는 것이 이 개정의 목적이다. 판정을 수신 측이
각자 구현하면 한 곳만 빠져도 안전이 조용히 열리므로, `shared/schemas` 의
`EstopState.is_engaged` 한 곳에 둔다.

엣지 쪽에서는 설정이 두 경우를 가른다.

| `estop.source` | 보고 |
|---|---|
| `none` | 장치가 없다고 **선언**했다 → `released`. 없다는 것은 지식이다 |
| `field_device` | 읽을 장치가 있다 → 읽을 때까지 `unknown`. 못 읽는 것은 무지다 |

## 3. §5 통신 상태 판정 — 배수에 하한

| 상태 | 0.2 | 0.3 |
|---|---|---|
| `degraded` | `gap > 3 × 주기` | `gap > max(3 × 주기, 20초)` |
| `offline` | `gap > 10 × 주기` | `gap > max(10 × 주기, 60초)` |

배수만 쓰면 발행이 빠른 장치일수록 판정이 조여진다. 2초 주기 로봇은 6초 침묵에 degraded 가
된다. 배치도를 촘촘히 보려고 주기를 내린 것이 통신 감시를 예민하게 만들면 안 된다.

배수·하한 모두 잠정치다 (OPN-04).

## 4. DB 반영 (마이그레이션 0006)

`db-schema.md` §3.2 `robot_status`, §3.6 `stop_event` 를 개정한다.

| 테이블 | 변경 |
|---|---|
| `robot_status` | `mission_state` → `phase`. CHECK 에서 `'error'` 제거 (4값). 오류는 기존 `error` JSONB 가 전담 |
| `stop_event` | `detail JSONB` 신설 — 물리 비상정지의 원 보고 `{estop, reason, source}` |

`stop_event.detail` 이 필요한 이유: `released_at IS NULL` 은 판정 결과이고 `detail.estop` 은
엣지가 실제로 뭐라고 했는지다. `unknown` 도 정지로 잡히지만 화면 문구는 "작동됨"이 아니라
"확인 필요"여야 한다. 사람이 읽는 `reason` 문구를 파싱하는 대신 기계가 읽을 자리를 만든다.

기존 `mission_state = 'error'` 행은 진행 단계가 이미 소실됐다. `phase` 를 `idle` 로 내리고
`error` 가 비어 있으면 `legacy_unknown` 표식을 채워 사실을 보존한다.
