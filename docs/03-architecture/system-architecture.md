# 03-1 · 시스템 아키텍처

서버는 1개가 아니라 역할이 다른 **애플리케이션 서버**와 **미들웨어 서버** 2개로 나뉜다. 엣지 원시 데이터(센서·로봇 상태 등)는 미들웨어 서버에 저장되고, 계정·세션·메모처럼 사용자가 직접 입력하는 데이터는 애플리케이션 서버에 저장된다 (두 저장소를 물리적으로 분리할지는 `component-internals.md` 참고).

기능(FR)별로 두 서버와 웹앱이 각각 무엇을 담당하는지는 `component-mapping.md`, 각 컴포넌트 내부 구성은 `component-internals.md`에서 다룬다.

## 1. 계층 구조

| 계층 | 구성 요소 | 통신 대상 |
|---|---|---|
| 웹앱 (브라우저) | 모니터링 대시보드, 제어 UI, 데이터 관리, 음성/LLM UI | 애플리케이션 서버 |
| **애플리케이션 서버** | 인증·세션, 관리자 메모·장비등록 등 사용자 입력 처리, 미들웨어 서버 결과를 웹앱에 전달하는 API/WebSocket 게이트웨이, 웹앱 서빙 | 웹앱, 미들웨어 서버 |
| **미들웨어 서버** | 엣지 데이터 수집·저장(DB), 통계·농업일지 생성, 영상 기반 AI 분석·음성 처리·LLM 연동 훅, 제어 명령을 엣지가 이해하는 형식으로 변환 | 애플리케이션 서버, 엣지 |
| 엣지 | 실물 하드웨어와의 통신 (2차년도는 임의 데이터 생성기, 3차년도 예정: 실제 엣지) | 미들웨어 서버 |

엣지 하위의 로봇·생육기 등 실물 하드웨어, 로봇 경로계획, AI 모델, 음성 인식 엔진은 개발 범위 밖이다.

## 2. 계층별 동작 방식

### 웹앱 ↔ 애플리케이션 서버
- 화면 갱신은 WebSocket으로 애플리케이션 서버가 푸시하는 최신 데이터를 받는다.
- 설정 변경·조회는 REST로 처리한다.

### 애플리케이션 서버
- 사용자 인증·권한을 관리한다.
- 관리자 메모 작성, 장비 등록·관리 등 사용자가 직접 입력하는 내용을 처리한다.
- 미들웨어 서버가 만든 결과(통계, 리포트, AI 분석 결과 등)를 웹앱이 원하는 형태로 전달하는 API/WebSocket 게이트웨이 역할을 한다.
- 웹앱을 서빙한다.

### 미들웨어 서버
- 엣지가 주기적으로 전송하는 데이터를 수신·저장(DB)한다. 센서값 하나하나를 즉시 애플리케이션 서버까지 중계하는 것이 아니라, 미들웨어 서버가 중간에서 저장·버퍼 역할을 한다.
- 통계 집계, 농업일지 생성, 영상 기반 AI 분석, 음성 처리, LLM 연동 등 **원시 데이터를 다루는 처리**를 담당한다. 이 데이터가 이미 미들웨어 서버 DB에 있으므로, 별도 서버로 옮기지 않고 여기서 처리한다.
- 애플리케이션 서버의 요청에 따라 처리 결과나 저장된 데이터를 전달한다.
- 애플리케이션 서버를 거쳐 들어온 제어 요청을 규격화된 명령으로 변환해 엣지로 전달한다.

### 엣지
- 2차년도에는 임의 데이터 생성기로 대체한다. 데이터를 주기적으로 미들웨어 서버에 전송하고, 미들웨어 서버의 제어 명령을 받아 실행하는 역할을 한다.
- 트레이(파레트) 반출·이동·작업·반납(로봇 임무)과 생육기 환경 제어를 포함한다.

## 3. 설계 원칙

1. 모든 외부 하드웨어는 엣지를 통해서만 미들웨어 서버와 통신한다.
2. 애플리케이션 서버는 미들웨어 서버를 통해서만 엣지 데이터에 접근한다 (애플리케이션 서버가 엣지와 직접 통신하지 않는다).
3. 엣지와의 통신은 인터페이스로 분리한다. 2차년도에는 임의 데이터 생성기 구현체를 연결하고, 이후 실제 엣지 구현체로 교체 가능해야 한다 (아래 구조 참고).
4. 데이터·명령 규격은 특정 필드 집합에 고정하지 않고, 확장 가능한 구조로 설계한다.

```
미들웨어 서버 코어 (데이터 수집/제어 명령 로직)
        │
        ▼
  엣지 통신 인터페이스
        │
        ├── 2차년도:  임의 데이터 생성기 구현체
        └── 3차년도:  실제 엣지 구현체 (예정)
```
