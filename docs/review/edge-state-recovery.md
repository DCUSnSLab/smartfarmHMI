# 끊겼다 붙었을 때 상태 복구

엣지 재시작 · 네트워크 단절 · 서버 다운 — 셋 다 "떨어졌다 다시 붙는" 같은 문제다.
붙는 순간 서버와 엣지가 서로의 현재 상태를 어떻게 다시 맞출지 정리한다.

## 판단 기준 하나

**그 값의 진실을 누가 갖고 있는가.**

| 원천 | 복구 방법 |
|---|---|
| 서버 | 서버가 retained 로 발행 → 엣지가 재접속하며 구독하면 브로커가 즉시 재배달 |
| 현장 하드웨어 | 엣지가 부팅 시 다시 읽는다. **못 읽으면 "모름"으로 보고**하고 안전측 판정 |
| 파일 | 엣지가 다시 읽는다 |
| 엣지 메모리뿐 | 복구 불가. 상태로 두면 안 되고 사건(알림·이력)으로 남긴다 |

원격 전체 정지(§4.6.1)가 첫 번째 형태의 본보기다. 서버가
`.../edge/{edge_id}/stop_state` 를 retained 로 발행하고 엣지가 구독한다.

## 시나리오 1 · 엣지 재시작

엣지 프로세스가 죽었다 살아난다. 브로커·서버는 정상.

재접속 시 엣지가 birth · 비상정지 상태 · 배치도를 다시 발행하고, 서버의
`stop_state` retained 를 받아 원격 정지를 복구한다. 여기까지는 설계대로다.

**문제는 위 표의 `✗`·`△` 들이다.**

- **#2·#3** 웹에서 목표 온도를 24도로 맞춘 뒤 엣지를 재시작하면 엣지는 잊는다.
  서버는 `device_control_setting.is_current` 에 24도를 그대로 들고 있어
  **화면과 실제가 어긋난 채 아무도 모른다.** `_handle_birth` 는 통신 상태만
  갱신하고 목표값을 다시 보내지 않는다.
- ~~**#5** `estop{false}` 로 시작한다. 외부 래치 장치가 ROS transient_local 로
  유지해 주면 복구되지만, 없으면 접속 즉시 서버에 `engaged: false` 를 보고한다.~~
  **해소 (2026-08-10, 스키마 0.3).** `estop` 이 세 값이 되어 부팅 직후에는
  `unknown` 을 보고하고, 서버·엣지 모두 이를 눌린 것으로 취급한다. 래치를
  실제로 읽어야 `released` 가 나간다.
- **#11~14** 임무 도중 죽으면 그 임무는 사라진다. 서버의 `command_log` 는
  `timeout_watcher` 가 실패 처리하지만, **엣지가 어디까지 했는지는 알 수 없다.**
  파레트를 들고 있었다면 그대로 멈춘다. (#13 오류 사유만 0.3 에서 사건으로
  빠져나오게 됐다 — 진행 단계 #11 은 그대로 남는다.)

## 시나리오 2 · 네트워크 단절

엣지는 살아 있고 브로커와의 연결만 끊긴다.

엣지는 `clean_session=true` 로 붙으므로 **끊긴 동안 발행한 메시지는 큐에 남지
않고 버려진다.** 대신 재접속할 때마다 현재 상태를 다시 발행한다
(`edge_node.cpp` 의 `set_on_connect` → `publish_estop`).

### 끊긴 동안 현장에서 비상정지를 해제하면?

| 상황 | 서버 인식 |
|---|---|
| 엣지 생존, 네트워크만 끊김 | ○ 재접속 시 `engaged:false` 재발행 → 정확히 복구 |
| **끊긴 동안 엣지도 재시작** | △ **"해제됨"과 "잊음"을 구분 못 함** |
| 끊긴 동안 눌렀다 풂 | △ 사건 자체가 소실 (현재 상태만 오므로) |

두 번째가 핵심 문제다. 두 경우 모두 서버가 받는 메시지는 `{"engaged": false}`
로 똑같다. 실제로는 아직 눌려 있는데 화면에서 정지가 풀린다.

**해결 — 반영됨 (2026-08-10, 스키마 0.3, `communication-interface.md` §4.7).**
`engaged: bool` 을 **`engaged` · `released` · `unknown`** 세 값 `estop` 으로
바꿨다. 하드웨어를 읽어 확인했을 때만 `released` 를 보내고, 못 읽으면
`unknown` 을 보낸다. 양쪽 모두 `unknown` 을 안전측(눌린 것)으로 취급하고,
화면에는 "현장 확인 필요"와 사유(`not_read_yet`·`read_failed`·`no_source`)를
띄운다. 하위호환 매핑은 두지 않았다 — 그 매핑이 곧 되살리려는 결함이다.

엣지 쪽에서는 `estop.source` 설정이 "장치가 없다고 **선언**한 구성"(→ `released`)과
"읽을 장치가 있는데 아직 못 읽음"(→ `unknown`)을 가른다. 없다는 걸 아는 것은
지식이고, 못 읽는 것은 무지다 — 후자만 안전측으로 실패해야 한다.

세 번째(사건 소실)는 상태만 보내는 구조의 본질적 한계다. 안전 기록이
필요하면 엣지가 전이 이력을 쌓았다가 재접속 시 올려보내야 한다 — 요구사항
확인이 먼저다.

## 시나리오 3 · 서버 다운

미들웨어만 죽는다. 브로커와 엣지는 정상.

서버도 `clean_session` 기본값(true)으로 붙으므로 **다운된 동안 발행된 메시지를
나중에 받지 못한다.** 재기동하면 `farmon/v1/#` 을 구독하고, 브로커가 retained
메시지만 즉시 재배달한다.

| 메시지 | retained | 다운 중 발행분 |
|---|---|---|
| 센서 telemetry | ✗ | **전부 소실** — DB 에 구멍 |
| 로봇 status | ○ | 마지막 값 1건만 복구 |
| birth · death | ○ | 복구 |
| 비상정지 · 원격정지 · 배치도 | ○ | 복구 |

센서값이 retained 가 아닌 것은 의도된 선택이다 (엣지 코드 주석: 초기값은 서버가
REST 스냅샷으로 제공). 다만 그 결과 **다운 시간만큼 시계열에 구멍이 남는다.**
복구할 방법은 지금 구조에 없다.

### 확인 필요 — 죽은 엣지가 살아 있는 것으로 보일 수 있다

서버는 `last_received_at` 을 메시지의 `timestamp` 가 아니라 **수신한 벽시계
시각**으로 기록한다 (`ingest.py`). 서버 재기동 시 브로커가 오래된 retained birth
를 재배달하면 그 순간 시각으로 찍혀 **3일 전에 죽은 엣지도 "방금 접속함"으로
보인다.**

정상 재접속한 엣지는 retained death 를 빈 발행으로 지우므로, 죽은 엣지에는
retained death 가 남아 있어 `_handle_death` 가 offline 로 되돌린다. 다만 birth 와
death 는 서로 다른 토픽이라 **재배달 순서가 보장되지 않는다.** death 가 먼저
오면 birth 가 덮어써서 online 인 채로 남는다.

실제로 재현되는지 확인이 필요하다.
